# ADR-0002 — Read-only Moonraker transport
Status: Accepted (G0), implemented as policy + mocked client · Date: 2026-11-05

**Decision.** `ReadOnlyMoonrakerTransport` exposes exactly: `get_server_info`, `get_printer_info`, `list_objects`, `query_objects`. Allowlist = `GET /server/info`, `GET /printer/info`, `GET /printer/objects/list`, `POST /printer/objects/query` (validated body). WS: only JSON-RPC `printer.objects.subscribe`, validated frame. Denied until a formal audit adds them: `GET /printer/objects/query`, WS `server.info`/`printer.info`, `server.connection.identify`. Target = literal RFC1918 IPv4:7125. `trust_env=False`, no redirects, size caps, owner `Consent` for real network. Verb is never trusted alone (the one allowed POST is body-validated).
**Why.** Cahier §6; Moonraker mutating calls exist on the same server (see source-audit §3).
**Consequences.** Some useful reads (identify, GET query) need an audit; the 192.0.0.0/8 trusted range upstream is wider than RFC1918 but we stay stricter. Checks live in `backend/app/transport/policy.py`; any new route = ADR amendment + negative test.
**Amendment 2026-11-05 (WebSocket).** `ReadOnlyMoonrakerWebSocket` (`backend/app/transport/ws.py`): only `subscribe()` can send, frame validated by `check_ws_message` before any I/O; no generic send; inbound parsed, capped (256 kB), never answered; `proxy=None`, no compression; same RFC1918:7125 + owner Consent rule. New dependency `websockets>=15,<16` (BSD-3, pure Python). Tests: `backend/tests/test_ws.py`. Not yet run against the real U1 (H-02 needs owner go).
**Not covered.** Real-hardware WebSocket behaviour (H-02).
**Amendment 2026-11-08 (audit, BACKLOG #52 L3/L4).** `POST /printer/objects/query` and `query_objects` are removed: the app never used them and they never ran on the machine. The allowlist is now GET only (`/server/info`, `/printer/info`, `/printer/objects/list`) plus WS `printer.objects.subscribe`; any POST is refused. The real WebSocket client is opened with `ping_interval=None`: no keepalive pings, so the only data frame sent is the subscribe message (the library still answers pings and closes cleanly).
**Amendment 2026-11-08 (BACKLOG #57 live rules, #59 connectivity self-check; owner decision: defensive code, UNTESTED).** Minimal widening, each item justified:
1. *One new GET:* `GET /server/files/directory?path=logs` (tag `server.files.directory`, method `get_logs_disk_usage`). Needed by rule S22 (log partition usage, forum topic 41445: logs and configuration share a 100 MB partition). Moonraker has no disk-usage-only route; this is the smallest documented one (`disk_usage` of the partition holding the root). Policy: new `ALLOWED_HTTP_QUERY` = exact path + exact key `path` + exact value `logs`; any other key, value, path or method is refused before I/O, and every other path still takes no query. Only `disk_usage.total/used/free` is kept; the file list is dropped unread. One read, not two: the forum describes one partition for config and logs (limit stated in the rule). A failure (404 on a printer without a `logs` root) only makes S22 say "not observable".
2. *No new request, wider subscribe:* the single subscribe frame also names `temperature_sensor cavity` (`temperature`) and `bed_mesh` (`probed_matrix`), both listed by the real U1 (H-01 object list) but never subscribed to on one. Policy: new `ALLOWED_SUBSCRIBE_OBJECTS`, exact object names; anything else is refused before I/O. Offsets, nozzle diameters, toolhead states and counters, `toolhead.estimated_print_time` and the frame `eventtime` were already in the H-02 subscription (all fields of `extruder*` and `toolhead`).
3. *Rejected:* `/machine/proc_stats` and `/machine/system_info` (host uptime is the frame `eventtime`; system_info carries network identifiers), `/printer/objects/query` (subscribe already gives the same objects), reading `configfile` (whole configuration, can exceed the 256 kB frame cap), a second directory read for `config`, any reconnect of the stream.
Budget: **4 GET + 1 WebSocket message; if the stream drops, up to 6 more status GET: 10 GET at most** (`app.live.MAX_GET`, `MAX_WS_SENT`; a tripwire stops the capture above it). The consent text (FR/EN) states these numbers and `tests/test_live_rules.py` fails if text and code disagree. Connectivity facts (latency per GET, drops, reconnects = 0 by design, address changed or not) come from these same requests. Tests: allowed and denied variants in `backend/tests/test_live_rules.py`. Not run against a real U1.
**Amendment 2026-11-08 b (BACKLOG #65 maintenance reminders; code only, UNTESTED until one supervised read-only check).** One more GET: `GET /server/history/totals` (tag `server.history.totals`, method `get_history_totals`), exact path, no query (the policy refuses any query on it, as on every path outside `ALLOWED_HTTP_QUERY`). Needed for reminders by print hours and job count: Moonraker keeps these totals in its history component and has no narrower route. Only `job_totals.total_print_time`, `total_jobs`, `total_filament_used` and `total_time` are kept (all four must be valid numbers, else nothing is kept); `longest_job`, `longest_print` and `auxiliary_totals` (provider and sensor names) are dropped unread. A failure (404 when the history component is off, any error) only makes the reminders say "not observable"; the capture goes on. Tool changes come from the `extruder*.switch_count` counters already in the subscribe (no new request; meaning not documented officially). Rejected: `/server/history/list` and `/server/history/job` (file names, per-job details), `/server/history/reset_totals` and job deletion (writes), a database read. Budget: **5 GET + 1 WebSocket message; if the stream drops, up to 6 more status GET: 11 GET at most** (`app.live.BASE_GET`, `MAX_GET`, `MAX_WS_SENT`; tripwire unchanged). Consent text FR/EN updated; `tests/test_live_rules.py` compares text and code. Tests: allowed and denied history variants, field filtering, 404 and malformed replies in `backend/tests/test_live_rules.py`.

**Amendment 2026-11-10 (BACKLOG #70, owner request; reverses the 2026-11-08 b rejection of `/server/history/list`).** Two more GET, both with one exact query: `GET /server/history/list?limit=20&order=desc` (tag `server.history.list`, method `get_history_jobs`) and `GET /server/gcode_store?count=100` (tag `server.gcode_store`, method `get_gcode_store`). Why: the status of the last jobs (`completed`, `cancelled`, `interrupted`, `klippy_shutdown`...) and the console error lines (`!! Timer too close`, `Lost communication with MCU`) are the facts support asks about, and no narrower route exists. The 2026-11-08 b rejection was about file names and per-job details: they are now dropped in memory (`app.live._jobs` keeps status, start/end UTC, durations, filament length, layer count, slicer name/version, filament type; file name, user, uuid, thumbnails and slicer settings are never read into the result; `app.live._console` keeps at most 20 error-like lines scrubbed with the log-import scrubber, the other lines are only counted). `job_history` and `console_errors` observations; no rule reads them yet. Probed read-only on the owner's U1 (firmware 2.1.0) on 2026-11-10: both answer 200. Still refused: `/server/history/job`, `reset_totals`, job deletion, any POST. Budget: **7 GET + 1 WebSocket message; if the stream drops, up to 6 more status GET: 13 GET at most** (`app.live.BASE_GET`, `MAX_GET`). Consent text FR/EN updated; tests compare text and code.

**Amendment 2026-11-10 b (BACKLOG #70, owner request: the support pack).** A second, separate scope: a transport built with `support=True` (only `app.supportpack` does it; the live capture never does, so its 7 + 6 budget is unchanged). Still GET only, still exact: `/machine/system_info`, `/machine/proc_stats`, `/machine/peripherals/usb`, `/server/temperature_store`, `/server/files/list?root=logs|config` (names and sizes), `/printer/objects/query` with allowlisted object names only (`SUPPORT_OBJECTS`: mcu versions, filament state, exception manager, defect detection...; never `configfile` or macros), and **file downloads** `/server/files/logs/<name>` and `/server/files/config/<name>` limited by regex to named files (klippy log and its numbered rotations, moonraker, unisrv, syslog, gui, mosquitto and flow_calculator logs; `printer.cfg`, `xyz_offset_calibration.cfg`, `snapmaker/*.json` calibration files, `persistent/*nozzle_config.json`). Refused: `moonraker.conf` and `gui_config.json` (may hold cloud settings), `print_task*.json`, any `gcodes` or `camera` root, `..`, `//`, `%`, any other name, any query on a download, any write. Caps: 12 MiB per file, 80 MiB in total, at most 3 klippy runs. Why: Snapmaker support asks for logs, versions and calibration; the touchscreen export is encrypted but the same logs are plain in Moonraker's `logs` root (probed read-only on the owner's U1, firmware 2.1.0, 2026-11-10). The pack is **not anonymous** (serial number optional, raw logs): IPv4, IPv6 and MAC addresses are removed from logs, configs and system info by default, the zip is AES-256 (pyzipper, WinZip AES, `pycryptodomex`) with a random 99-bit password shown once and never stored, the zip lives in memory (latest only). Member names stay readable (AES zip limit). About 20 requests in about 45 s. Route `POST /api/v1/support/pack` needs `consent: true` and the app header, shares the one-capture-at-a-time lock. Tests: `backend/tests/test_supportpack.py` (policy allow/deny, caps, redaction, partial failures, password, API) and `frontend/tests/support-pack.test.tsx`. Run once on the real U1 through the UI: 39 files, 7.3 MB, 0 IP/MAC left in logs.
